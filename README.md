# JD Major Filter

JD Major Filter 是一个 Chrome 浏览器插件，用来帮助非理工科背景的产品岗求职者快速筛选招聘官网里的 JD 专业门槛。

它会扫描岗位列表页或详情页中的 JD 文本，识别是否出现「计算机 / 软件工程 / 理工科 / 数学统计 / 人工智能 / 数据科学」等专业背景要求，并给岗位打上风险标签，支持隐藏高风险岗位和导出 CSV。

## 适用场景

这个插件主要面向校招产品类岗位筛选，例如：

- 产品经理
- AI 产品经理
- 用户产品
- 内容产品
- 增长产品
- 商业产品
- 策略产品
- 平台产品
- 工具产品

第一版优先支持：

- 字节跳动招聘官网
- 腾讯招聘官网
- 小红书招聘官网

其中字节跳动招聘页已经做了专门适配。腾讯和小红书目前保留通用适配与详情页手动扫描能力，后续需要继续做真实页面验证和 DOM adapter 优化。

## 判断结果

插件会把岗位分成 5 类：

| 标签 | 含义 | 默认处理 |
| --- | --- | --- |
| ✅ 可优先投递 | 没有发现明确理工科、计算机、软件工程等专业限制 | 显示 |
| 🟡 可尝试，但有风险 | 有 AI、AIGC、技术理解、数据分析等要求，但没有明确专业限制 | 显示 |
| 🟠 高风险，默认隐藏 | 出现计算机、理工科、数学统计等专业关键词，即使写的是「优先」也按高风险处理 | 可隐藏 |
| ❌ 明确排除 | 明确要求相关专业背景，例如「要求计算机相关专业」 | 可隐藏 |
| ⚪ 需点开复核 | 页面无法提取完整 JD，或规则无法稳定判断 | 显示 |

重要规则：

只要 JD 出现「计算机 / 软件工程 / 理工科 / 电子信息 / 自动化 / 人工智能 / 数据科学 / 数学 / 统计学」等专业词，即使后面写的是「优先」「加分」「preferred」，第一版也会标记为 🟠 高风险，而不是普通提醒。

## 核心功能

- 扫描当前岗位列表页
- 从当前页开始扫描 3 页，也就是当前页 + 后两页
- 打标签 badge
- 默认隐藏 🟠 高风险和 ❌ 明确排除岗位
- 当前详情页手动扫描
- 导出 CSV
- 区分岗位来源页码，避免混页导出
- 扫描进度显示
- 后续页预扫失败时保留已完成结果，不直接清空当前页
- 按筛选条件隔离缓存，避免不同城市、不同岗位条件的结果混在一起

## 字节跳动页面的扫描逻辑

字节招聘页不是简单的静态 HTML。岗位详情数据由字节前端接口动态渲染，而且接口带 `_signature` 签名，不能直接用普通 `fetch` 稳定请求。

因此插件当前使用更稳的方式：

1. 在列表页识别当前可见岗位卡片和详情页链接。
2. 先用列表页已经显示的文本做快速判断，立即打第一版标签。
3. 对不确定岗位，在隐藏 iframe 中打开详情页。
4. 让字节自己的前端完成接口签名、数据请求和页面渲染。
5. 插件读取隐藏详情页中已经渲染出来的「职位描述 / 职位要求」主体文本。
6. 用本地规则重新分类，并更新标签与 CSV 结果。

这样做不需要后端，也不需要破解字节接口签名。缺点是深度扫描会慢一些。

## 分页扫描逻辑

「扫描当前页起 3 页」不是扫描第 1、2、3 页。

正确逻辑是：

如果用户当前在第 5 页，插件会扫描：

```text
第 5 页 + 第 6 页 + 第 7 页
```

当前页会立即打标签；后两页会在后台隐藏扫描。用户之后翻到第 6 页或第 7 页时，如果缓存里已有结果，插件会自动回填标签。

这是为了让用户可以每 3 页点一次插件，同时不打断当前浏览位置。

如果后两页里的某一页因为页面加载、网络或招聘站限制读取失败，插件会保留已经扫到的岗位，并在 Popup 里显示提醒。它不会因为后续页失败就清空当前页结果。

字节列表页翻页时会重新渲染岗位卡片，原先插入的 badge 会随旧 DOM 消失。插件会监听页面变化，并在新卡片渲染出来后从缓存自动回填标签。

## CSV 导出

支持 3 种导出：

- 导出可投岗位：✅ + 🟡
- 导出高风险 / 排除岗位：🟠 + ❌
- 导出全部岗位

CSV 字段：

- `company`
- `title`
- `location`
- `url`
- `result`
- `risk_level`
- `matched_keywords`
- `matched_sentence`
- `reason`
- `should_hide_by_default`
- `page_number`
- `scanned_at`

导出边界要求：

- 只导出当前扫描任务的结果
- 不混入旧页面结果
- 不混入详情页底部「相关职位」
- 不混入其他城市或其他筛选条件下的缓存结果
- 导出文件名会自动带上平台和时间，方便区分不同扫描批次

## 本地开发

安装依赖：

```bash
npm install
```

构建扩展：

```bash
npm run build
```

构建完成后会生成：

```text
dist/
```

Chrome 加载扩展时选择 `dist` 文件夹。

## 在 Chrome 中加载插件

1. 打开 Chrome。
2. 进入 `chrome://extensions/`。
3. 打开右上角「开发者模式」。
4. 点击「加载未打包的扩展程序」。
5. 选择本项目的 `dist` 文件夹。
6. 打开招聘官网岗位列表页。
7. 点击浏览器右上角的 JD Major Filter 插件图标。
8. 点击「扫描当前页岗位」或「扫描当前页起 3 页」。

如果修改了代码，需要重新执行：

```bash
npm run build
```

然后回到 `chrome://extensions/`，点击 JD Major Filter 卡片上的刷新按钮。

## 常见问题

### 为什么扫描比较慢？

因为字节详情页的数据不是普通 HTML 里直接给出的，而是由字节自己的前端接口渲染出来。插件为了稳定拿到完整「职位要求」，会在隐藏 iframe 中打开详情页并等待渲染完成。

当前已经做了两阶段提速：

- 先用列表页文本快速打标签
- 再只对不确定岗位做详情页深扫

### 为什么不是直接调用字节 API？

字节前端接口带 `_signature`，普通请求不带签名时会失败或返回错误页面。直接复现签名属于更高维护成本的逆向方案，不适合作为第一版稳定商业交付。

### 为什么只扫当前页或当前页起 3 页？

这是为了保证扫描范围可控，避免结果混页、混城市、混筛选条件。商业化版本需要优先保证结果可信，而不是一开始就全站批量爬取。

### 扫描完成但页面上没看到标签怎么办？

先确认：

1. 是否刷新了 `chrome://extensions/` 里的插件。
2. 是否刷新了招聘页面。
3. Popup 里统计数字是否变化。
4. 当前筛选模式是否隐藏了 🟠 或 ❌。

如果统计变化但页面没有标签，通常是 DOM adapter 需要针对该招聘站页面结构继续优化。

## 技术栈

- Chrome Extension Manifest V3
- React

- 无后端

## 当前限制

- 字节跳动适配优先级最高，腾讯和小红书仍需更多真实页面验证。
- 页面结构变化可能导致 adapter 需要维护。
- 深度扫描依赖隐藏 iframe 渲染，速度会受招聘站页面加载速度影响。
- 当前不做全站批量爬取。

## 商业化交付原则

这个插件按商业产品标准维护，核心原则是：

- 不把「本地构建通过」说成「目标网站已验证可用」
- 不混入旧页面、相关职位、其他页码或其他城市的数据
- 不打断用户当前浏览位置
- 扫描范围必须和用户预期一致
- 导出结果必须可追溯到页码和扫描时间
